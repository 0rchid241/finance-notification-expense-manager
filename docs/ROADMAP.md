# Master Roadmap — 금융 알림 기반 개인 지출 관리 시스템

> 목표: **2026-10-31까지 실제 Android 기기에서 핵심 흐름이 끝까지 동작하는 Release Candidate 완성**

이 문서는 프로젝트의 **진행률 기준(Source of Truth)** 이다.  
세부 일정은 `weekly-plan.md`, 설계는 `architecture.md`, 요구사항은 `requirements.md`를 따른다.

## 진행률 계산 규칙

- 전체 진행률은 아래 세부 항목의 **가중치 합계(100%)** 로 계산한다.
- `[x]`는 기본 브랜치에 구현·테스트·문서 등 완료 근거가 확인되는 경우에만 표시한다.
- 단순 파일 생성, 작업 중 브랜치, 미병합 PR, 아이디어만 있는 상태는 완료로 계산하지 않는다.
- 부분 완료는 자동으로 임의 퍼센트를 주지 않는다. 항목의 완료 기준을 충족했을 때 해당 가중치를 반영한다.
- 기능 범위가 바뀌면 총합 100%를 유지하도록 가중치를 함께 조정한다.

## M0. 프로젝트 기반 — 5%

- [x] **1%** GitHub 저장소 및 Android / Backend 기본 구조 구성
- [x] **1%** Android 프로젝트 기본 실행 구조 확보
- [x] **1%** Spring Boot 프로젝트와 health check 구성
- [x] **2%** README / 요구사항 / 아키텍처 / 주간 계획 문서화

**완료 기준:** 신규 개발자가 저장소만 보고 프로젝트 목적, 구조, 실행 단위를 이해할 수 있다.

---

## M1. 원본 금융 알림 수집 — 15%

- [x] **4%** `NotificationListenerService` 등록 및 실제 알림 이벤트 수신
- [x] **3%** package / title / text / postedAt 등 원본 필드 추출
- [x] **4%** Room 기반 Raw Notification 저장소(Entity / DAO / Repository) 및 기본 테스트
- [ ] **1%** 사용자 알림 접근 권한 안내 / 설정 진입 UX
- [ ] **1%** 금융 알림 후보 필터 및 null·무의미 알림 처리 정책
- [x] **1%** Backend raw notification 수신 API
- [ ] **1%** Android → Backend 실제 원본 알림 전송

**완료 기준:** 실제 금융 알림 1건이 Android에서 안정적으로 수집되고, 원본 데이터가 손실 없이 저장·전송된다.

---

## M2. 알림 해석 및 정규화 — 20%

- [ ] **3%** `RawNotificationRequest/Event` 계약 확정
- [ ] **3%** `NormalizedFinancialEvent` 모델 정의
- [ ] **4%** 첫 금융 앱/결제수단 파서 구현
- [ ] **3%** 두 번째 이상의 알림 형식 지원 및 Parser 분리 구조
- [ ] **2%** 금액 / 가맹점 / 거래 유형 / 발생 시각 / 출처 추출
- [ ] **2%** 해석 실패·미확정 이벤트 별도 처리
- [ ] **3%** 정규화 자동 테스트와 실제 샘플 검증

**완료 기준:** 서로 다른 금융 알림이 동일한 표준 이벤트 구조로 변환되고, 해석할 수 없는 알림은 정상 거래로 강제 변환되지 않는다.

---

## M3. 거래 정합성 처리 — 20%

- [ ] **3%** Transaction 모델과 상태(APPROVED / CANCELLED / REFUNDED 등) 정의
- [ ] **4%** 동일 이벤트 재처리 idempotency
- [ ] **4%** 동일 실제 거래의 다중 알림 / 중복 후보 판별
- [ ] **4%** 승인 취소 원거래 매칭
- [ ] **2%** 환불 및 기타 상태 전이 처리
- [ ] **3%** 정합성 핵심 케이스 자동 테스트

**완료 기준:** 중복 알림은 거래를 중복 생성하지 않고, 취소·환불 이벤트가 가능한 경우 원거래와 연결되어 일관된 상태를 유지한다.

---

## M4. 사용자 정의 소비 규칙 — 15%

- [ ] **3%** Rule 도메인 모델 및 저장 구조
- [ ] **3%** 기간 / 카테고리 / 금액 / 횟수 조건 표현
- [ ] **4%** 거래 반영 후 활성 Rule 평가 엔진
- [ ] **2%** Rule 생성 / 조회 / 활성화 관리 API
- [ ] **3%** 경계값·누적값·중복평가 자동 테스트

**완료 기준:** 사용자가 만든 규칙이 코드 하드코딩 없이 데이터로 저장되고 실제 거래에 의해 결정론적으로 평가된다.

---

## M5. 가계부 UI 및 거래 관리 — 10%

- [ ] **3%** 거래 목록 조회 UI
- [ ] **2%** 거래 상세 / 상태 표시
- [ ] **2%** 카테고리별 지출 요약
- [ ] **1%** 잘못 처리된 거래 확인·수정 최소 흐름
- [ ] **2%** Android ↔ Backend 조회 API 통합

**완료 기준:** 사용자가 앱에서 처리된 거래와 기본 소비 현황을 확인할 수 있다.

---

## M6. 피드백 및 End-to-End 통합 — 5%

- [ ] **2%** 규칙 충족 Feedback 생성
- [ ] **1%** Android에서 피드백 표시
- [ ] **2%** 실제 알림 → 정규화 → 정합성 → 규칙 → UI 전체 E2E 검증

**완료 기준:** 실제 금융 알림 하나가 들어온 뒤 사용자가 앱에서 거래와 규칙 피드백을 확인할 수 있다.

---

## M7. 안정화·테스트·Release Candidate — 10%

- [ ] **2%** 주요 실패 경로와 예외 처리
- [ ] **2%** 개인정보 최소수집·로그 점검 및 기본 보안 검토
- [ ] **2%** 핵심 비즈니스 로직 테스트 보강
- [ ] **1%** Android 권한 / 오류 UX 정리
- [ ] **1%** Release APK/AAB 빌드 및 실제 기기 검증
- [ ] **1%** README / 아키텍처 / 데모 문서 최신화
- [ ] **1%** 최종 발표·시연 시나리오 검증

**완료 기준:** 새 환경에서 실행·시연 가능하며 핵심 기능의 실패가 앱 전체 장애로 이어지지 않는 Release Candidate가 존재한다.

## 현재 기준 진행률

기본 브랜치에서 확인된 체크 항목 기준: **17%**

> 이 값은 체크리스트 근거가 바뀔 때만 갱신한다. “많이 작업했다” 같은 체감 진척은 퍼센트에 반영하지 않는다.
